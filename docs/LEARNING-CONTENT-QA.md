# Learning content production and quality protocol

Status: proposed implementation contract for zabankhan-learn. The owner is an independent developer and French learner; no teacher, native-speaker reviewer or external tester is guaranteed. This protocol does not certify linguistic accuracy. Runtime remains offline-first and LLM-free.

## 1. Source policy
Build a source registry before generation. Candidate references (not yet audited): CEFR Companion Volume for outcomes; Inventaire linguistique des contenus clés des niveaux du CECRL for French syllabus; Édito and progressive FLE textbooks for coverage inspiration only; OQLF Vitrine linguistique, Académie française and CNRTL for rules/usage; FLELex and Lexique 3 for lexical difficulty; France Éducation international for current exam specifications. Candidate reusable datasets: Wiktionary, Tatoeba, Universal Dependencies, Wikisource, Common Voice and open FLE resources. Check each edition, dataset, license, attribution, access and redistribution terms independently. Public access is not permission to redistribute. Do not copy textbook exercises, proprietary audio or official exam questions. Existing 897 TCF prompts require provenance and license audit before redistribution. Store source ID, title, URL, edition, section, access date, license and permitted use; retain only permitted excerpts. Verify source claims against actual source, never fabricated citations. Mark conflicting or unsupported claims blocked.

## 2. Curriculum and reference packets
Map each concept to a measurable outcome, CEFR range (not a universal mandated grammar syllabus), prerequisites, rule scope, exceptions, register, contrastive examples, common errors, and exercise objectives. Separate target language, explanation locale and UI locale. Each reference packet contains verified rule claims with source locators, approved examples or licensed data, known ambiguity and prohibited assumptions. Do not generate outside packet scope. A lesson includes explanation, examples, contrasts, common mistakes, guided practice, independent practice, transfer task, assessment and review. Production tasks are self-assessed unless a reliable deterministic key exists.

## 3. Risk tiers and production strategy
- Low risk: deterministic inflection, gender or spelling from verified licensed lexical data; constrained transformations of approved sentences; dictation using approved text; explicit tense/form instructions. Validate exceptions and accepted variants. Ordering can have multiple valid sequences; enumerate or reject.
- Medium risk: contextual grammar selection, translations, reading comprehension, vocabulary senses, short original dialogues. Require source-grounded explanation, independent solution, ambiguity review and owner review. Prefer questions with evidence spans in the supplied text.
- High risk: subtle register, idioms, advanced grammar, open-ended translation, exam scoring, authentic pronunciation judgments, C1/C2 content. Keep draft or defer until adequate expertise/evidence exists; no automated free-text proficiency score. Do not market synthetic TTS as authentic exam audio.
Generate small batches (10–20 items) and prioritize deterministic templates over unconstrained generation. A validated sentence can yield multiple activities but tag shared stimulus IDs and avoid counting them as independent mastery evidence.

## 4. Pipeline
1. Curate sources and reference packet; record licenses and exact claim locators.
2. Generate original structured draft with explicit objective, answer, rationale, distractor rationale, accepted variants and evidence.
3. Blind independent solver receives prompt/context/options but not author key or rationale. Record answer and uncertainty.
4. Adversarial reviewer searches for alternate valid answers, ambiguity, unnatural language, wrong explanation, translation errors, level mismatch and unsupported claims. Use a different model family when practical; no requirement to pay for four providers. Disagreement or uncertain answer blocks publication; consensus alone is not evidence.
5. Deterministic checks: schema, IDs, references, graph cycles, answer/options consistency, normalization, duplicates, lexical/inflection checks where data supports them, evidence spans, locale coverage, licensing and pack integrity. Grammar tools are advisory, not proof. Test accepted variants and rejected answers. Never auto-correct content silently.
6. Owner performs source-assisted review of each pilot item and checks learner usability; record uncertainty honestly. If unable to verify, quarantine rather than guess. No claim that owner is an expert. External specialist review is optional future work; distinguish it from owner review.
7. Publish only eligible items via CI; generate manifest, QA report and immutable pack. Feedback and corrections follow versioned release process.
All model calls are maintainer-side, optional provider adapters; no keys in repo or app, no user data. Log model/version, prompt version, reference packet hash and outputs as permitted. Cache runs, cap budget, support dry runs and manual/offline authoring.

## 5. Metadata and release gates
Each item: stable id, revision, concept/skill, level estimate, stimulusId, objective, source refs, provenance, license, generation method, answer spec, feedback, locale, risk tier, validation evidence, reviewer role, review date, content hash, status. States: draft -> machine_validated -> owner_reviewed -> approved_for_pilot; expert_reviewed is a separate optional assurance flag, not inferred. rejected/quarantined excluded. Any material edit invalidates previous approval and checks. Machine-only content stays in development fixtures, not default public learning packs. Pilot release requires verified sources/license, passing checks, independent solution and ambiguity review for generated items, explicit owner approval, no unresolved findings. High-risk items require stronger evidence or specialist review; defer if unavailable. CI fails closed if metadata missing, approval stale, or unresolved issues. Public pilot labeled experimental, not professionally certified. Provide item-level report mechanism (ID/version, optional comment; no automatic personal data collection), quarantine known faulty items and publish corrected versions. Preserve progress across revisions; invalidate affected scores where appropriate.

## 6. Examples and failure modes
Ambiguous: “Quand tu arriveras, je ___ mon travail.” Both terminerai and aurai terminé can be valid depending on intended chronology. Reject unless context/instruction uniquely specifies target. Controlled form exercise: “Complétez au futur antérieur : D’ici vendredi, nous ___ la rédaction du rapport.” Key aurons terminé; measures form recognition, not spontaneous tense selection. For semantic transfer use a clear timeline and independently check alternatives. Test wrong keys, multiple correct options, malformed elision, accent-sensitive contrasts, wrong translations, unsupported citations, unnatural distractors, repeated stimulus leakage and inappropriate level labels.

## 7. Reference benchmark and scaling
Start with 3–5 concepts and 30–50 carefully checked items, one short reading and one listening activity; expand toward 20 concepts, 200 grammar items, 10 readings, 50 comprehension questions, 10 listening activities and 50 vocabulary exercises only as capacity allows. Owner-reviewed reference set is a provisional benchmark, not expert gold standard. Keep a separate held-out set and deliberately defective fixtures with known errors. Measure defect detection by category, false rejection, unresolved disagreements, cost per approved item and owner review minutes. Synthetic defects do not establish real-world accuracy. Do not tune and evaluate on identical examples. No numerical accuracy claim without independent evidence. Stop scaling if review backlog or unresolved defects grows. At 2 minutes per item, 200 items take ~6.7 hours and 2,000 ~66.7 hours excluding lessons, source research and corrections; reduce volume rather than skip gates.

## 8. Repository layout
zabankhan-learn owns references/, curriculum/, schemas/ (pinned runtime contract), benchmark/, prompts/{generation,verification,adversarial-review}/, pipeline/ (generate, solve, verify, validate, publish), content/ (language-organized source items with explicit status), reports/, tests/, catalog/, and CI workflows. Keep one canonical item rather than duplicate draft/reviewed copies; generated public artifacts include only approved items. Keep private or nonredistributable evidence outside public Git history. License decision remains with owner. App repository owns runtime schemas and small fixtures; no runtime AI. GitHub Pages is proposed delivery, with versioned immutable packs, configurable origin, and no generated ZIP history unless necessary.

## 9. Implementation sequence
P0 audit existing resources and provenance; create registry and curriculum scope. P1 define schema, reference packet format, validation and benchmark fixtures; author tiny real pilot before freezing renderer contract. P2 build exercise engine against those fixtures in parallel with content review. P3 implement pack build and release gates, offline download integration. P4 release small pilot across structured, targeted and exam practice paths only where content passes gates; exam guides may link official sources without redistributing unlicensed questions. P5 expand only after defect and workload review. Full mocks, advanced levels and external specialist review remain future options. No repository initialization, pipeline code, content generation or license selection is performed by this documentation change.
