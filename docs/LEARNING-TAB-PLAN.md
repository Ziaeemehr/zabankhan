# Zabankhan Learning Tab — Product and implementation plan

Status: proposal, not implementation. No runtime changes authorized by this document.

## 0. Current state (findings from the first audit pass)
These facts come from the code on this branch and change several decisions below. P0 must confirm and complete them.
- **Navigation:** the bottom bar already has five tabs (`home`, `library`, `words`, `review`, `settings` in `App.kt`). Five is the practical maximum for a phone bottom bar, so a sixth "Learn" tab is not an option without merging or demoting an existing one (see §4).
- **Bundled content:** French data is bundled in `composeResources/files/fr` (~4.1 MB: lexicon, `grammar/notes.json`, `grammar/posters.json`, `exams/exams.json`, `exams/tcf-questions.json`, starter `dataset/`). `LanguageDataPacks` reads only from a hard-coded `bundledPacks` map; its own comment says to move to downloadable per-language packs when a second language gets data.
- **Existing downloads:** datasets (word decks, graded stories) and dictionary packs are already downloaded from `ziaeemehr.github.io/zabankhan-dict/...` via a `manifest.json`. So `zabankhan-dict` already hosts pedagogical content, not only lexical data, and an HTTPS + manifest download path already exists.
- **Exams:** `exams.json` describes TCF variants (TP, Canada, Québec, IRN) with sources and a `checkedOn` date; `tcf-questions.json` holds 897 speaking/writing prompts (EE1–3, EO2–3) with Persian translations. There is no objective (multiple-choice) item bank yet. Provenance and licence of the prompt bank must be recorded before it is reused in a published pack.
- **Persistence:** Room schema version 11 already has `ExamAttempt` (examId, questionId, answer, score, note, lang) and backups count exam attempts. Vocabulary uses a 5-box Leitner scheduler (`srs/VocabSrs.kt`).
- **Platform helpers already in common code:** okio `sha256()`, an `expect/actual` zip inflater (`content/ZipArchive.kt`, Android + iOS), Ktor, kotlinx-serialization. There is no Unicode NFC normalizer in common code yet.

## 1. Product positioning
Zabankhan is a companion to textbooks, classes and independent reading, not a replacement for teachers or a clone of Duolingo. Its differentiator is the integration of reading, dictionary, TTS, video, Leitner and structured practice. The existing grammar notes, grammar posters, exam guides and TCF prompt bank (§0) are reused and linked from the new learning area, not rebuilt. No runtime LLM, API key, subscription or automatic AI-generated lessons is required. AI may assist maintainers offline during authoring, subject to review. Optional user-authored imports are a later convenience, not a core dependency.

All runtime code is language-agnostic: language-specific behaviour goes through `LanguageSpec`, never a hard-coded `"fr"`. French is only the first content language.

## 2. Three learning paths
All paths share a concept catalog, content bank, exercise engine and learner profile. Users may switch paths without losing progress.
- **Structured course / Parcours guidé:** CEFR-aligned A1–B2 supplemental progression (extensible to C1/C2) inspired by communicative textbooks (Édito, Alter Ego+, Tendances), not a reproduction or claim of full CEFR coverage. Select level, browse units, skip familiar material, revisit concepts. Each unit combines communicative objectives, grammar, vocabulary, pronunciation, reading, listening, oral and written production, culture and a bilan.
- **Exam preparation / Préparation aux examens:** independent profiles for TCF IRN, TCF Tout Public, TCF Canada/Québec, DELF A1–B2, DALF C1–C2 deferred beyond current scope, TEF variants later. Build on the existing `exams.json` profiles and TCF prompt bank. Choose target and optional date, practice by skill, learn strategies, take timed mock sections and review errors. Verify current official format, duration, scoring and skill requirements for each variant before publication, and store the checked date (as `exams.json` already does). TCF/TEF results are attestations of level, not diplomas. Keep practice mode distinct from exam mode (no dictionary, hints or pause where official rules disallow them). Scores are unofficial; do not claim calibrated CEFR or official equivalence. Speaking/writing use prompts, rubrics, model answers and self-assessment; no automatic proficiency claims.
- **Personalized learning / Entraînement ciblé:** choose concepts from a textbook or class, grammar, vocabulary, listening, reading, pronunciation, workplace or daily life. Search by topic, level and concept; build a daily plan from selected concepts, due reviews and errors. Optional textbook mappings by edition/unit are bibliographic pointers only, not copied content.

## 3. Curriculum
Use CEFR Companion Volume descriptors as outcomes; use multiple textbooks as inspiration for progression, not as content sources. Consult Grammaire progressive, Vocabulaire progressif, Phonétique progressive and Grammaire en dialogues for coverage planning. Produce original texts and exercises. Maintain a matrix of level, communicative outcome, concept, prerequisite, skill and assessment. CEFR does not mandate a universal grammar syllabus. Map new concepts to existing grammar note IDs so a lesson can open the matching note instead of duplicating it.
Suggested B1 sequence (illustrative): memories (passé composé / imparfait contrast); relationships (relative pronouns); work/study (reported speech); culture (conditional, including future-in-the-past); feelings (subjunctive); media (passive); environment (cause/consequence); travel (pluperfect); technology (concession); regrets (past conditional); future plans (future perfect); argumentation (connectors). A1 starts with introductions and basic transactions; A2 expands everyday autonomy; B2 emphasizes argumentation and nuanced comprehension; C1/C2 explicitly out of current content scope; schemas, level identifiers, navigation and pack contracts must support future additions without a runtime redesign.
Example unit: Culture et spectacles — listen to an original concert dialogue, read a review, study criticism vocabulary, learn the conditional as future-in-the-past, practice intonation, record an opinion, write a short review, complete a bilan. Each micro-lesson takes roughly 5–15 minutes.
Example: « Avant le concert, j’espérais que ce serait une expérience inoubliable. » Explain the conditionnel présent as future-in-the-past (a future seen from a past viewpoint); contrast with the futur simple in direct speech (« J’espère que ce sera… ») and with the imparfait for simultaneity (« …que c’était… »); provide examples and contextual exercises. Saving banal, inoubliable, s’attendre à to vocabulary review is an explicit user action that reuses the existing save flow.

## 4. UX and navigation
The bottom bar is already full (§0). Decide in P0 between: (a) a Learn hub reached from Home (continue card, daily plan, paths) with no new tab — recommended first step; (b) merging `review` into a new `learn` tab that contains vocabulary review, lessons and error review; (c) moving `settings` out of the bar into a top-bar action to free a slot. Do not ship a sixth tab.
Landing: active language/level, continue last activity, daily plan, three paths, downloaded content, progress and error review. Empty state offers a small starter pack and its download size. Allow browsing without enrollment. Lesson: objective, short explanation, tappable text, TTS, examples, common errors, practice, summary. Reuse existing reader/dictionary/Leitner interactions (`TappableLearningText`, dictionary sheet, vocab save) rather than duplicate them. Exercise UI: progress, answer input, submit, feedback explaining why, next, retry later. Exam UI: timer, section navigation, submission confirmation, post-exam review.
Follow the project UI rules: no horizontally scrolling menus or chip rows — level, path, skill and filter choices wrap (`FlowRow`) or go in a dropdown. Text direction follows the content (Persian RTL, French LTR) without flipping the whole screen. Support English UI, dark mode, accessibility, large fonts, tablet layouts and screen-reader labels. Avoid punitive streaks; optional goals and reminders reuse the existing review reminder.
Daily plan default 15 min: 5 new concept, 4 practice, 3 Leitner, 3 error review. Configurable time and rest days; prioritize overdue reviews by reallocating the daily budget, but never block manually selected new lessons.

## 5. Exercise engine
Data-driven renderer registry, deterministic scoring and separate practice/exam policies, all in `commonMain`. MVP: single/multiple choice, true/false, gap fill, ordering, matching, reading comprehension, TTS listening and dictation. Later: conjugation tables, error correction, translation with accepted variants, recorded shadowing (reuse the existing shadowing/mic code) and self-assessed production. Normalize Unicode NFC, whitespace and punctuation according to question policy; preserve meaningful accents and apostrophes (treat ’ and ' as equivalent), allow explicit alternatives; never silently accept wrong grammar. NFC needs an `expect/actual` (Android `java.text.Normalizer`, iOS `NSString.precomposedStringWithCanonicalMapping`), and common code must not use the `\p{M}`/`\p{N}` regex classes that Kotlin/Native does not support. Provide hints, explanations, distractor rationales, stable item IDs and seeded shuffling. TTS is synthetic and not a substitute for authentic exam audio. Open answers without reliable keys are self-assessed. Save attempts and resume interrupted sessions; do not count retries as independent first attempts.

## 6. Learner model and adaptive review
Track per language: selected level, goals, completed activities, attempts, concept/skill evidence, review due dates, exam sessions and downloaded packs. Keep vocabulary scheduling in the existing 5-box Leitner system; concept/error review is separate but coordinated in the daily plan. Use transparent rules: prioritize due errors, then weak concepts with sufficient evidence, then the next eligible lesson; mix previously unseen items and spaced retrieval. Example intervals 1/3/7/14 days, reset to the first interval after an error. Show sample counts and recent first-attempt accuracy, not unsupported mastery percentages. A concept graph supports prerequisite remediation (futur simple stem and imparfait endings before conditional morphology; semantic use taught separately). Hard prerequisites must form an acyclic graph. Initial level self-selection; later a diagnostic by skill with stated uncertainty and no claims for untested speaking/writing.
Storage: new Room tables (attempts, review state, enrollment, installed packs) in a schema 11 → 12 migration with exported schema and a migration test like `BatchAMigrationTest`. Extend or map the existing `ExamAttempt` table for exam sessions instead of adding a parallel one. Backups (local and Drive) include learning progress, stable IDs and pack references, not redownloadable assets; test restore and merge behaviour, and decide whether learning progress joins library sync.

## 7. Repository decision (proposed ADR)
Options:
- **App repo:** convenient for schemas, tests and tiny fixtures but couples content releases to app releases.
- **zabankhan-dict:** already serves dictionary packs *and* datasets (decks, stories) over GitHub Pages with a manifest, so the app already trusts this origin and download path. Adding learning packs there is the lowest-cost start, at the price of mixing lexical and editorial lifecycles in one repo.
- **Dedicated zabankhan-learn:** independent versions, contributions, validation and multi-language growth, but a new origin, CI and release flow.
Recommendation: create dedicated **zabankhan-learn** for independent versions, contributions, validation and multi-language growth, keeping content location configurable (§8). zabankhan-dict can serve as a temporary origin only if the owner prefers to delay the new repo. The owner has created zabankhan-learn; this is the selected content repository. Either way the app repo owns the runtime contract, schema compatibility and small fixtures. Reference dictionary data by lemma/language and resolve locally with graceful fallback; never copy it into learning packs.
A separate repo alone does not reduce APK/IPA size: exclude full packs from bundled assets and download on demand. Generalize `LanguageDataPacks` into one pack manager that serves bundled and downloaded packs (grammar, exams, lexicon, learning) rather than building a second, parallel download system.
Proposed content layout (in whichever repo hosts it):
    catalog/
    schemas/ (generated or pinned from app contract)
    courses/<lang>/{A1,A2,B1,B2}/
    concepts/<lang>/
    exercises/<lang>/
    exams/<lang>/{tcf-irn,tcf-tp,delf}/
    media/
    tools/
    licenses/
    tests/
Delivery: start with the existing GitHub Pages origin and manifest pattern. GitHub Release assets redirect to a different host (`objects.githubusercontent.com`), which can be slower or unreachable for some users, if Releases are used later, keep a mirror base URL configurable. Pack files are immutable per version (version in the path); the catalog is the only mutable file. Do not use Git LFS for runtime delivery. Keep source JSON/Markdown human-editable; compile to compressed JSON or SQLite after measuring query performance. Split by language, level and unit/skill; optional audio packs separate. Shared concept IDs and dependencies avoid duplication across paths. Tiny starter content only if the measured bundle budget permits.

## 8. Pack contract and download lifecycle
Manifest fields: packId, language, level, kind, version, schemaVersion, minAppVersion, dependencies, compressedBytes, installedBytes, sha256, asset URL, locale availability, license, attribution. Catalog version and trusted origin pinned; HTTPS, SHA-256 verification (okio), optionally a signed catalog with a pinned key for stronger authenticity. Stable content IDs are never reused; version changes preserve progress; aliases/migrations for renamed concepts; retired items remain interpretable in history. Reject unsupported schema, missing dependencies, path traversal (zip-slip), oversized archives and invalid references. Download to a temporary location, verify size/hash, validate schema, atomically install; keep the old pack on failure. Support cancellation, retry, low storage, offline use, update notifications, removal and redownload without losing progress. Never execute downloaded code or scripts. Restrict remote media and links; use local TTS by default. No learner data sent to the content host beyond ordinary download requests. All of this lives in `commonMain` with Ktor, okio and kotlinx-serialization (no `java.*`, `android.*` or `org.json`), and must not depend on Google Play services. The `bazaar` flavor is planned for removal (see P0); the learning feature does not add any flavor-specific code.
Initial engineering targets (measure before committing): starter fixture under 1 MB compressed, text-only unit packs under 2 MB compressed where practical; audio separately listed. Show actual sizes and storage use. Test interrupted downloads, corruption, incompatible versions, low storage, offline launch and update rollback.

## 9. Data model
Entities: Concept(id, language, CEFR range, prerequisites, outcomes, grammarNoteIds); Lesson(id, conceptIds, blocks, locale, duration, source/license); Exercise(id, type, prompt, context, options, answerSpec, feedback, conceptIds, skill, difficulty, mediaRefs); Unit(id, objectives, ordered lessonIds); Path(id, unitIds, selection policy); ExamProfile(id, variant, formatVersion, sections, time limits, scoring policy, official source and checked date); Attempt(id, itemId, itemVersion, timestamp, firstAttempt, outcome); ReviewState; PackManifest. Localize explanations separately from target-language text. Use stable IDs across Persian/English translations. Validate referential integrity, prerequisite cycles, correct answers, duplicate items, accessibility metadata and licensing.
Example exercise (illustrative, not a released question): id `fr.b1.future-in-past.001`; context « Hier, avant le concert : »; prompt « J’espérais que ___ une expérience inoubliable. »; options `ce serait` / `ce sera` / `ce soit` / `c’était`; key `ce serait`. Each option includes its pronoun so elision stays correct (`ce était` is not French). Rationales: `ce sera` breaks sequence of tenses after a past main verb; `ce soit` — *espérer* takes the indicative in the affirmative; `c’était` is grammatical but expresses simultaneity, so the context must make the future reading the only one — if it cannot, accept both or drop the item. Tags fr, B1, grammar, future-in-past.

## 10. Content production and QA

See [Content production and quality protocol](LEARNING-CONTENT-QA.md) for the binding pilot workflow and release gates. In case of conflict, the protocol supersedes the general QA description below.
Define syllabus and coverage matrix first. Adopt a source-first acquisition strategy: prioritize existing licensed educational materials and authentic texts, then external references and independently authored complementary activities, then grounded generation only for gaps. See the QA protocol for acquisition and rights gates. Authors create original content; an optional maintainer-side LLM generates drafts using the structured schema. Automated checks for schema, references, answer keys, duplicates, missing feedback, localization and licenses. There is no dedicated linguistic or native-speaker reviewer. Content quality rests on (1) automated checks, (2) the owner's source-assisted review of each pilot item before release (not expert linguistic certification), and (3) a limited tester who checks only the scope the owner assigns (for example, a specific unit or a usability flow). Because review capacity is small, the content pilot is kept small and items with any doubt about the answer key are dropped rather than reviewed further. Never treat model agreement as proof. Record author, reviewer (the owner or the tester, as applicable), revision, provenance and license. Do not copy commercial textbook texts/exercises/audio or official exam papers without permission; use original exam-style questions and official public format specifications. Apply the same provenance check to existing bundled content (e.g. the TCF prompt bank) before moving it into a published pack. Select an explicit content license only after owner decision; third-party assets retain their own compatible terms. Publish via CI only after review; support error reports and corrected pack releases.

## 11. Implementation phases and acceptance gates
P0 — complete the audit started in §0: grammar/exam assets and their provenance, navigation option (§4), Room schema and backup/sync, reader/TTS/dictionary APIs, existing dataset/dictionary download code, `LanguageDataPacks`, and Android/iOS parity. Produce reuse map and ADR; confirm repository, delivery origin and licence choices.
P1 — schema, fixtures, validation CLI, local repository interface, NFC `expect/actual`, exercise scoring tests, stable IDs. Gate: invalid content rejected, deterministic scoring, no network/LLM needed, `iosSimulatorArm64Test` and `linkDebugFrameworkIosArm64` pass.
P2 — Learn entry point, concept browser, lesson renderer, exercise UI, progress and error review, Room migration. Gate: A1 and B1 sample units complete offline on Android/iOS; dictionary and Leitner reuse; RTL/dark/accessibility tested; migration test passes.
P3 — catalog and on-demand pack manager (generalized `LanguageDataPacks`), backup/restore integration, release pipeline. Gate: install/update/delete/corruption/rollback tested on the remaining build; APK/IPA size measured against baseline; progress survives updates and restore.
P4 — pilot French supplemental bank: 20 concepts across A1–B1, ~15–20 reviewed items each, one complete A1 and B1 unit, original reading/listening samples. Gate: owner-reviewed content, automated checks passing, no ambiguous keys, and usability feedback from the owner and, if available, a limited tester on the sample unit. This is not full level coverage.
P5 — expand A1–B2, daily planner, concept graph and targeted practice; optional diagnostics. Gate: due reviews, weak-topic selection, path switching and evidence counts tested.
P6 — exam prep pilot (choose TCF IRN or DELF B1/B2 based on demand; TCF reuses the existing profiles and prompt bank), verified exam profile, timed sections and self-assessment rubrics. Gate: format verified against current official sources, no official score claims.
P7 — additional exam variants within A1–B2 and languages; C1/C2 only after a separate scope decision; optional validated lesson import/export for externally authored content. No runtime AI required.
Every phase passes the project verify gate: `assemblePlayDebug`, `testPlayDebugUnitTest`, `iosSimulatorArm64Test`, `linkDebugFrameworkIosArm64` (drop `assembleBazaarDebug` once the flavor is removed).
Long-term indicative content targets, not commitments: 100 concepts, 2,000 exercises, 100 reading and 100 listening activities, 50 vocabulary sets and 10 mock exams. Expand only after quality and usage evidence.

## 12. Testing and success metrics
Unit tests: scoring, normalization, scheduler, graph, migration, schema compatibility. Integration: pack lifecycle, offline operation, dictionary lookup, Leitner save, backup restore, exam timing. UI: Android/iOS, RTL, dark mode, large text, interruption/resume, accessibility; emulator tests use the `.debug` package. Content: automated validation for every release, plus the owner's review of each new item and the limited tester's checks on the scope assigned to them. Measure locally (or opt-in only) lesson completion, return to practice, review completion, first-attempt accuracy on unseen items, download failures and installed size; no mandatory analytics or collection of personal study content. Compare learning outcomes cautiously; engagement is not proficiency.

## 13. Non-goals and open decisions
No full textbook replacement, no runtime LLM, chatbot, automatic free-text grading or mandatory account. No claim of official CEFR certification. The content repository already exists; no code implementation or asset migration in this documentation branch. Owner decisions: navigation option (§4), delivery origin, licence, starter pack budget, first exam variant, supported locales, audio strategy and whether learning progress syncs. Technical estimates depend on P0 audit; no schedule or staffing commitment yet.
